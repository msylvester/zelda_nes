## Codebase Patterns
- Specs go in the `specs/` directory as markdown files, one per user story
- PRD lives at `prd.json` — update `passes` and `notes` fields when a story is complete
- All game measurements are in pixels, sub-pixels (1/16th), or half-hearts
- NES resolution: 256x240, playable area: 256x176 (64px for HUD)
- Tile grid: 16x16 pixels per tile
- No build/test toolchain yet — quality checks are N/A for spec-only stories
- TypeScript interfaces in specs use consistent naming: `PascalCase` for types, `camelCase` for fields
- Tile data is stored in row-major flat arrays (index = row * 16 + col)
- Door states in dungeons must be symmetric between connected rooms
- All animation timings are defined in frames (1 frame = 1/60s at 60 FPS NTSC)
- Sprite priority layers: 0 (ground items) through 7 (screen effects); Link is always priority 4
- Canvas uses `imageSmoothingEnabled = false` for pixel-perfect NES rendering
- NES sprite flicker (8 sprites/scanline limit) should be emulated for authenticity
- Input uses `KeyboardEvent.code` for physical key location, not `KeyboardEvent.key`
- Action buttons are edge-triggered (fire on key-down transition), not held/level-triggered
- Input is polled once per frame at start of game loop; all systems read a frozen `InputSnapshot`
- Game phase + player state together determine which inputs are accepted (two-level filtering)
- Enemy behavior is fully data-driven via archetype objects — no per-enemy hardcoded logic
- Movement patterns and attack patterns are separate concerns (enemies can move and attack on independent timers)
- Bosses don't count toward the 6-enemy screen limit and are generally not knockbackable
- Standard enemies have 0 invincibility frames after damage; bosses have 8 frames
- Darknut shielding is directional — must compare attack direction vs enemy facing direction
- PRNG for enemy behavior is seeded per-screen for reproducibility
- Save state vs runtime state: only data that must survive session restarts goes in SaveFile; screen-local entities/positions are runtime-only
- On continue/load, HP restores to 3 hearts (not max) — NES-accurate behavior
- localStorage is the persistence backend; save data is JSON-serialized with a saveVersion field for migrations
- Audio uses Web Audio API with OscillatorNode (pulse/triangle) and AudioBufferSourceNode (noise) to approximate NES APU
- SFX always override music on shared channels; music resumes on that channel after SFX completes
- AudioContext requires user gesture to resume (browser autoplay policy) — register one-shot listener on first interaction
- Triangle channel has no volume control (on/off only) — matches NES hardware
- Mute state is NOT persisted in save data; resets to unmuted on page load
- Audio update runs once per frame after render in the game loop
- The final one-shot PRD lives at specs/final-one-shot-prd.md and is the implementation reference
- Implementation uses Vite + TypeScript strict + Vitest + ESLint (no other deps)
- All assets are procedurally generated at runtime via AssetGenerator — no copyrighted files committed
- Module structure: src/ with core/, input/, world/, entities/, combat/, rendering/, animation/, audio/, inventory/, progression/, screens/, data/, assets/, utils/
- Game loop order per frame: input poll → phase transitions → entity updates → collision → damage → screen transition check → render → audio update

- **Learnings for future iterations:**
  - Use `KeyboardEvent.code` (physical key location), not `KeyboardEvent.key` (character output) for consistent behavior across keyboard layouts
  - Direction priority uses a stack model — most recently pressed direction wins, releasing pops from stack to reveal previous direction
  - Action buttons (A, B, Start) are edge-triggered (`justPressed`), not level-triggered (`held`) — matches NES behavior where holding a button doesn't auto-repeat
  - Browser `keydown` events with `event.repeat === true` must be filtered out to avoid false re-triggers
  - Must call `event.preventDefault()` on mapped keys to stop arrow keys from scrolling the page and Enter from submitting forms
  - Focus/blur handling is critical: clear all held keys on blur to prevent "stuck key" bugs, auto-pause on blur to prevent gameplay while tabbed away
  - Input acceptance varies by game phase (GAMEPLAY, PAUSE, TRANSITION, etc.) AND by player state within gameplay (IDLE, ATTACKING, KNOCKBACK, etc.) — two levels of input filtering
  - Inventory cursor skips empty cells (uncollected items) and wraps at grid boundaries

- **Learnings for future iterations:**
  - NES APU has 5 channels but Zelda only uses 4 (2 pulse, triangle, noise) — DMC is unused
